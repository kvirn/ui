# Accessibility contract: RadioGroup (RadioGroup.Root, .Radio, .Reveal, .Legend, .Prose, .HelpText, .ErrorMessage)

- **APG pattern:** [Radio Group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/). Native: `<input type="radio">` elements that share a `name` already give the pattern's keys (one Tab stop, arrows move and check, Space checks) and its roles, so no ARIA and no key handler are added. The group is a `<fieldset>` with a `<legend>` instead of `role="radiogroup"`.
- **Deviations:** none from APG. Design decisions: the group is a Fieldset, option labels carry no optional marker, **no `aria-invalid` on radios**, and the group holds no form state.
- **Native elements used:** `<fieldset>` and `<legend>` (`RadioGroup.Root` and `RadioGroup.Legend`), `<input type="radio">` (`RadioGroup.Radio`), `<label for>` (`Field.Label`).
- **Status:** alpha candidate. Accessibility-reviewer APPROVE. Manual AT is `pending`.
- **Tests:** `radio-group.test.tsx` next to this file. `radio-group.stories.tsx` in `apps/storybook/src/components/radio-group/`. The fieldset parts (`RadioGroup.Legend`, `RadioGroup.ErrorMessage`, `RadioGroup.Prose` as the description and `RadioGroup.HelpText` as the help text): `fieldset.a11y.md`. They are the Fieldset's parts under the group's name.

A RadioGroup is one question with exactly one answer ("How long do you need the permit?": 1, 6 or 12 months). `RadioGroup.Root` renders the `<fieldset>` and acts as a `Fieldset.Root` with `group` set; `RadioGroup.Radio` is a native radio. It holds no form state: the selected value is the `value` prop, and each change is reported up.

Rules, tested in `radio-group.test.tsx`:

- **The group is named by its legend and described by its help text and error** (`radio-group.test.tsx › the group is named by its legend and described by its help text and error`). The description is a `RadioGroup.Prose` above the options and the help text a `RadioGroup.HelpText` under them (the `Fieldset.HelpText` under the group's name): the description is the text content, so keep both short and plain, and a help text has no links. A Prose or HelpText directly in the group describes the group, one inside an option's Option describes that radio, and a Prose that isn't a description goes outside the group. An option's help text is a `Field.HelpText` in the option's `RadioGroup.Option`, in the small text size, directly under the label and outside the click target (`radio-group.test.tsx › an option help text is a Field.HelpText in that RadioGroup.Option, outside its label, and has no axe violations`). `RadioGroup.HelpText` is listed after the description and before the error (`radio-group.test.tsx › RadioGroup.HelpText is the group’s help text: after the description, before the error`).
- **One name, native grouping.** Every radio has the group's `name`, so the browser groups them. Without `name`, the group generates one (`useId`) (`radio-group.test.tsx › every radio gets the group’s name, generated when missing`).
- **Controlled by `value`.** The radio whose `value` equals the group's `value` is checked. `null` means "controlled, nothing selected". A change calls `onValueChange(value, { reason: 'input', event })` with the radio's value. The group never stores it (`radio-group.test.tsx › a controlled group checks the radio whose value it is given`).
- **Uncontrolled without `value`.** `defaultValue` sets `defaultChecked` on one radio; the browser keeps the state and a form submit sends it (`radio-group.test.tsx › uncontrolled: defaultValue and the form submit`).
- **No `aria-invalid` on radios** (ARIA 1.2 doesn't support it on `radio`). An invalid group sets `data-invalid` on the fieldset, its parts and every radio, so the theme can draw a thicker edge that does not rely on colour; the error reaches users through the fieldset's `aria-describedby` (`radio-group.test.tsx › invalid styles every radio and sets no aria-invalid`).
- **`required`** removes the optional text (in `en`, "(optional)") from the legend and sets `data-required`. No `aria-required` (not supported on `group` or `radio`); see Known issues.
- **`disabled`** on the group is native `fieldset[disabled]`. A single disabled `Radio` is skipped by Tab and by the arrow keys (native) (`radio-group.test.tsx › a disabled radio is natively disabled`). This is native radio behaviour, as the APG keyboard practice expects: an `aria-disabled` radio would be checked by the browser's own arrow keys. Put the reason in the option's help text.
- **`RadioGroup.Reveal` (the "Other, please specify" field).** `<RadioGroup.Reveal value="other">` follows its radio's `RadioGroup.Option` in the DOM and is `hidden` until the radio with that `value` is checked, so the field is next in the reading and Tab order (1.3.2) (`radio-group.test.tsx › the reveal is hidden until its radio is checked`, `radio-group.test.tsx › the reveal follows its radio’s option in DOM order`). It is never unmounted: the typed text survives switching options (`radio-group.test.tsx › checking another radio hides the reveal again and keeps what was typed`) and a plain form still submits it, so ignore or clear it on the server when its radio is not the chosen one.
- **The radio points at the reveal.** While a Reveal for it is mounted the radio has `aria-controls` with the Reveal's id; the id is stable, so it never points at nothing. No `aria-expanded`: not supported on `radio` (`radio-group.test.tsx › the radio points at the reveal with aria-controls, the others do not`).
- **Focus never moves.** Choosing the radio does not move focus into the field (3.2.2); the arrow keys keep moving through the radios (`radio-group.test.tsx › focus stays on the radio when the field appears`).
- **Selected value for the reveal.** Controlled: the group's `value`. Uncontrolled: the group mirrors the radio the user chose (starting from `defaultValue`) as UI state only, and goes back to `defaultValue` when the surrounding `<form>` resets (`radio-group.test.tsx › a form reset removes the field from the reading order`).
- **No key handler.** Roving focus, wrapping and checking on arrow keys are the browser's, and tested in the Keyboard table below (for example `radio-group.test.tsx › Tab leaves the group after one stop` and `radio-group.test.tsx › ArrowDown and ArrowRight move to the next radio and check it, wrapping`). No page handler cancels a key.

## Keyboard

- **Focus strategy:** native
- **Selection follows focus:** yes (native: an arrow key moves focus and checks the radio; instant and harmless, as the APG allows)
- **Arrows wrap:** yes (native: from the last radio back to the first, and the reverse)
- **Shortcuts:** none

The group is one Tab stop (a composite widget). The browser's own roving is used instead of `tabindex`: the checked radio, or the first (last, going backwards) when none is checked, is the stop. Home and End do nothing; they are not part of the APG radio group.

## Focus management

- Initial focus: not moved.
- Trap: no.
- Restore to: not applicable.
- On error: the group never moves focus. An ErrorSummary moves focus to itself; without one, the consumer moves focus to the checked radio, or the first one, of the invalid group.
- Never obscured by: nothing around the circles clips the focus ring (2.4.11 Focus Not Obscured (Minimum), AA).

## Announcements

One, only with a `RadioGroup.Reveal`: every time the user checks a radio and its field appears, the polite live region says "An input field has appeared below." once (`radioGroup.revealShown`, overridable per provider and per instance). It has no throttle key, so a second group, or returning to the radio within three seconds, is announced too. Nothing is said on first render with a checked radio, when `value` changes from outside, or when the field is hidden (`radio-group.test.tsx › it is announced politely, exactly once, when the user checks the radio`, `radio-group.test.tsx › it is not announced on mount with a checked radio`, `radio-group.test.tsx › it is not announced when a controlled value is set from outside`, `radio-group.test.tsx › it is not announced when the reveal is hidden`, `radio-group.test.tsx › the message can be overridden per instance`). Otherwise nothing is live. On entering the group a screen reader reads the legend, "group", the help text and, when invalid, "Error: …"; then the radio's label, "radio button", "1 of 3" (from the native grouping) and its state.

## Consumer responsibilities

- A `RadioGroup.Legend` that asks the question, first in the Root; a `RadioGroup.Option` with a direct-child `RadioGroup.Radio` and a `Field.Label` per option; a `value` on every Radio.
- Offer an answer for everyone. If "none" or "I don't know" is valid, it's an option; the group has no deselect.
- Preselecting an option is a decision with consequences (residents rarely change a default): do it only when one answer is overwhelmingly common and harmless.
- Pass `value` and `onValueChange` from your form state, or `defaultValue` and `name` for a plain `<form>`.
- Set `invalid` and render a `RadioGroup.ErrorMessage`. On submit, move focus to the checked radio or the first one of an invalid group (or to the ErrorSummary).
- With a `RadioGroup.Reveal`, put it right after its radio's `RadioGroup.Option`, give its field a label of its own, and make the field required only while its radio is chosen. A hidden field is still submitted: ignore or clear it when another option is chosen.
- Don't use a radio group for a long list: from about 7 options, a Listbox is shorter to scan.
- Say once, before the first question, that every question must be answered unless it says it is optional (in `en`: "Every question must be answered unless it says (optional)"), per 3.3.2 Labels or Instructions (A).

## Visual / modes

- Focus indicator: the default theme draws an outline around the circle, at least 2px thick, with at least 3:1 contrast against its background (2.4.7 Focus Visible, AA). Keep it if you restyle.
- Target size: the circle is at least 24 by 24 CSS pixels (2.5.8 Target Size (Minimum), AA). The whole row is the click target: the label spans the row, and the row is taller in comfortable density than in compact density.
- Colour: the circle has an edge with at least 3:1 contrast against the page (1.4.11 Non-text Contrast, AA). Checked is a dot inside a ring, so the shape carries the state, not only colour (1.4.1 Use of Color, A). Invalid is a thicker edge plus the error message. Disabled is a dashed edge, and a checked disabled radio keeps its dot in the muted text colour.
- forced-colors behaviour (a mode where the system chooses the colours): the dot is drawn as a filled shape, and the colours are set explicitly: a checked radio uses the system's highlight colour for its edge and dot, an invalid one a thicker edge in the system's text colour, and a disabled one the system's greyed-out text colour.
- The Reveal has an inline-start bar and indent that tie it to its radio; a border stays visible in forced colours. It does not animate.
- reduced-motion behaviour: the edge and fill change with a transition only when motion is allowed; the dot appears instantly.
- RTL (right-to-left text): the circles are at the right of their labels; the arrow keys are mirrored by the browser (see Keyboard).

### What to check

With a screen reader and the keyboard, try:

- Tab into the group: the legend and "group" are read.
- One Tab lands on the checked radio, or on the first if none is checked.
- The arrow keys move focus and check the radio, and wrap. A disabled option is skipped. In a right-to-left page the arrows are mirrored.
- Checking "Other" reads "An input field has appeared below." once, and Tab reaches the field.

## Known issues

- **A required group isn't announced as required.** `aria-required` isn't supported on `group` or `radio`, and KvirnUI prefers `aria-required` over native `required`. The group's legend loses its optional text and gets `data-required`. If the AT run shows a gap: `role="radiogroup"` on the fieldset (allowed on `<fieldset>`, and it supports `aria-required` and `aria-invalid`), or native `required` on the radios.
- **A radio has no focus state of its own.** `useRadio` returns no `isFocusVisible` and `RadioGroup.Radio` sets no `data-focus-visible`: a radio's focus state would make the browser stop treating the group as one Tab stop. The theme styles focus with the native `:focus-visible`.
- **`aria-describedby` on a `<fieldset>` isn't announced consistently by TalkBack.** See the Fieldset page.
- **Shift+Tab into an unchecked group.** Browsers differ on which radio gets focus: Chrome and Firefox focus the last, Safari the first. The keyboard tests run on Chromium; the optional engines run in CI.
