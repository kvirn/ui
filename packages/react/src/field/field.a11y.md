# Accessibility contract: Field (Field.Root, Field.Label, Field.ErrorMessage, Field.Prose as the description and Field.HelpText as the help text)

- **APG pattern:** none. There is no APG pattern for form fields. A field is native HTML: `<label for>`, a native control, and `aria-describedby` for the description, the help text and the error. Errors go through `aria-describedby`, not `aria-errormessage`.
- **Deviations:** none from APG. A Prose in a Field is the description (there is no Field.Description), and a help text is its own part, `Field.HelpText`. Errors are not live, and the optional marker and the error prefix are part of the accessible text.
- **Native elements used:** `<div>` (Field.Root), `<label for>` (Field.Label), `<p>` (Field.ErrorMessage), a `<div class="kv-prose">` for the description (Field.Prose), a `<p class="kv-field-help-text">` for the help text (Field.HelpText), a `<span>` for the optional marker and one for the error prefix, and a decorative `<svg>` (the `error` Icon) in the Field.ErrorMessage.
- **Tests:** `field.test.tsx` next to this file. `field.stories.tsx`, `label.stories.tsx` and `error-message.stories.tsx` in `apps/storybook/src/components/`. The control itself has its own contract: `text-input.a11y.md`.

A Field joins one control to its visible label, an optional description (`Field.Prose`), an optional help text (`Field.HelpText`) and an error message. The parts register with their Field, so no DOM query and no global id is involved, and the control's `aria-describedby` never names a part that isn't rendered. The consumer validates and sets `invalid`: there is no validation engine.

Registration rules:

- `aria-describedby` is every description's id (Prose and HelpText alike) in DOM order, then the error id, joined by a space, and only for the parts rendered. The order is the DOM order, whichever order the parts mounted in. With the default order that is the description, the help text, then the error. When none is rendered the attribute is absent, never empty. A screen-reader user hears the description, the help text, then "Error: …" in English, whatever the visual order.
- A `Field.HelpText` registers like a `Field.Prose`, takes `data-invalid` and `data-disabled` from the Field and nothing else from its state (the theme never styles them), is never focusable and is no live region. Outside a Field or Fieldset it gives the dev warning `help-text-outside-field` once and renders a `<p class="kv-field-help-text">` with no id. A help text is plain text: no link, list or heading in it. There is no dev warning for rich content.
- A `Field.Prose` inside a Field is the description of its control. Registration is automatic and has no opt-out: a Prose that isn't a description goes outside the Field.
- The description is the Prose's **text content**. A heading, list or link inside it is read as plain text, without its role or structure, and a link in a description can't be followed from there. Keep a description to plain text and a few short paragraphs, and put anything with structure outside the Field. A help text is plain text only.
- Each description and help text has its own id (a generated suffix on the control's id), so no two share one. A Prose or HelpText that unmounts leaves `aria-describedby` at once: it never names a missing id.
- A Prose outside a Field or Fieldset has no id and gives no warning, unlike a HelpText.
- A Field with two ErrorMessages gives a dev warning (they share one id): render one, with all the text.
- `Field.ErrorMessage` renders nothing while the Field isn't `invalid`, so a hidden or stale message is never referenced. A Field that is `invalid` without a Field.ErrorMessage gives a dev warning (3.3.1 Error Identification (A)).
- A Prose, a HelpText and the Field.ErrorMessage attach to the nearest Field or Fieldset. A Field inside a Fieldset (an option, a date box) therefore owns its own help text and error, and the Fieldset's own Prose, HelpText and Field.ErrorMessage stay the group's.
- A Fieldset's `invalid` never passes down to the Fields inside it.
- `useField({ hasDescription: true })` or `useField({ descriptions: ['above', 'under'] })` sets `aria-describedby` from the first render, so server-rendered markup is complete. With `descriptions`, spread `getDescriptionProps(name)` on each description or help text: its class is `kv-prose` (for a help text, set `className="kv-field-help-text"` after the spread), its id is `<controlId>-description-<name>`, listed in the order of the array, then the error. The Root component learns about its parts when they mount, so for a moment before hydration the server HTML has the parts but not the association. Use the hook for server-critical markup.

## Keyboard

- **Focus strategy:** native
- **Selection follows focus:** n/a
- **Arrows wrap:** n/a
- **Shortcuts:** none

Field.Root, Field.Label, the description (Field.Prose), the help text (Field.HelpText) and Field.ErrorMessage handle no keys and move no focus. Focus stays on the control, which owns its keys: see the TextInput and NumberInput contracts. Enter, Space, Escape, the arrow keys, Home and End are not handled by Field.

## Focus management

- Initial focus: not moved.
- Trap: no.
- Restore to: not applicable.
- On error: Field never moves focus. On submit, the form moves focus to the first invalid field, or to an ErrorSummary. The consumer does this, and the docs say so.
- Never obscured by: Field renders no overlay. Consumers with a sticky header set `scroll-padding` (2.4.11 Focus Not Obscured (Minimum) (AA)).

## Consumer responsibilities

- Keep a help text short and plain: one or two short sentences or a format example, text only, with no link, list or heading (see above). Anything the user must read before answering is a description (`Field.Prose`). A Prose that isn't a description, such as an article or a list of links, goes outside the Field. A help text is never the only place a format lives: the error repeats it. Its copy in a disabled or read-only field says why.
- Give every control a visible label (Field.Label) that describes what to enter (2.4.6 Headings and Labels (AA)). A placeholder is not a label (3.3.2 Labels or Instructions (A)). Put examples in a `Field.HelpText`, not in a placeholder.
- Set `invalid` and render a Field.ErrorMessage together. Write the message so it says what's wrong and how to fix it, in the field's own words, never blaming the user (3.3.1 Error Identification (A), 3.3.3 Error Suggestion (AA)). Plain text only: the icon, the prefix and the text lay out as one line.
- Set `required` on every required field. Required fields carry no visible marker, and optional ones say "(optional)". Use `marker="none"` where that text is wrong, such as a lone search field or a single consent checkbox. If you mark required fields yourself with an asterisk, add your own text that explains it, and use `marker="none"`.
- Keep a Field's control a direct child of `Field.Root` when it is a checkbox or radio: the default theme finds its layout from `.kv-field:has(> .kv-checkbox, > .kv-radio)`.
- Validate on submit, not on every key. Then move focus to the first invalid field, or show an ErrorSummary (3.3.1 Error Identification (A)).
- Render the parts in the default order: label, description, control, help text, then the error, so the visual order is the `aria-describedby` order (1.3.2 Meaningful Sequence (A)). A help text always goes under the control: text the user must read before answering is a description (`Field.Prose`) above it. With the error under the control, keep `scroll-padding` on the page (the end value leaves room for the message), so the on-screen keyboard or an autocomplete list doesn't hide it when the field gets focus (2.4.11 Focus Not Obscured (Minimum) (AA)). The order is the consumer's: another order keeps working.
- Use `autocomplete` on controls that ask for the user's own data (1.3.5 Identify Input Purpose (AA)), and never block paste (3.3.8 Accessible Authentication (Minimum) (AA)).
- A Field.Label whose text is in another language goes in a nested `KvirnProvider` with `useLocale().localeProps` on your own element (3.1.2 Language of Parts (AA)).
- Give a Field the `controlId` you need to link to it, for example from an error summary. Don't pass an `id` to the control inside a Field: the Field's id wins and a dev warning says so.

## Visual / modes

- Focus indicator: on the control (see the TextInput contract). Labels and text parts aren't focusable. An invalid text input keeps its error-coloured edge when it has focus, and shows the focus ring on any focus, a click included.
- Target size: the label is the click target for choice controls, taller than the 24 by 24 CSS pixel minimum in both densities, and sits above a text control (2.5.8 Target Size (Minimum) (AA)).
- Colour: the label, description, help text and optional marker use the normal text colour, and a help text keeps it when the field is invalid, disabled or read-only (the error carries the state). The error text has at least 4.5:1 contrast on every background (7:1 in the high-contrast themes), checked by the theme's contrast check. The error has an icon, and a text prefix for screen readers, and the invalid control has a thicker edge, so colour is never the only cue (1.4.1 Use of Color (A)). The invalid edge has at least 3:1 contrast against the page and card backgrounds (1.4.11 Non-text Contrast (AA)).
- forced-colors behaviour: the error text uses the system's text colour, the icon follows it, and the invalid control keeps its thicker border.
- reduced-motion behaviour: no layout animation when an error appears. Not checked by an automated sweep.
- 1.4.12 Text Spacing (AA): no fixed heights. A help text's size and line height are in `rem`, so it grows with the browser's text size (1.4.4 Resize Text (AA)).
- Help text size: a help text is a step smaller than a description in both densities. The size belongs to the part, not to where it sits.
- RTL: logical properties only. The icon doesn't mirror.

## WCAG SCs covered

- 1.3.1 Info and Relationships (A): native `<label for>`, description and error in the accessible description (`field.test.tsx › wiring: name and description per state`).
- 2.4.6 Headings and Labels (AA): the label describes the purpose of the control (consumer's text).
- 1.3.5 Identify Input Purpose (AA): the consumer's `autocomplete` passes through (see the TextInput contract).
- 1.4.1 Use of Color (A): invalid is a thicker edge, an icon and a message that starts with a text prefix.
- 1.4.3 Contrast (Minimum) (AA), 1.4.11 Non-text Contrast (AA): the pairs in the theme's contrast check (the error colour as text and as a 3:1 edge).
- 2.5.3 Label in Name (A): the visible label text, including "(optional)", is the name.
- 3.3.1 Error Identification (A): the message in text, with a text prefix, linked by `aria-describedby`.
- 1.3.2 Meaningful Sequence (A): with the default order the visual order is the spoken order: description, help text, then the error.
- 3.3.2 Labels or Instructions (A): a visible label always, and the description and help text linked to the control.
- 3.3.3 Error Suggestion (AA): the consumer's message text (the docs show the patterns).
- 4.1.2 Name, Role, Value (A): the control's name, description, `aria-invalid` and `aria-required`.
- 2.4.7 Focus Visible (AA): the control shows the focus ring on any focus, an invalid one included (Visual / modes; the control's own tests are in the TextInput contract).
- 2.5.8 Target Size (Minimum) (AA): the label is taller than 24 by 24 CSS pixels (Visual / modes; reviewed in the stories, no named test).
- 1.4.4 Resize Text (AA): the help text is in `rem` (Visual / modes; no named test).
- 3.1.2 Language of Parts (AA): a label in another language is marked by the consumer (see Consumer responsibilities).

### What to check

With a screen reader and the keyboard, try:

- Tab to the box: the label is read, then the description and the help text.
- A field that is not required reads "(optional)" at the end of its name.
- Submit the form empty: "Error:" and the message are read when focus arrives.
- Click the label: the box takes focus.
- On a phone with the keyboard open, the error under an invalid field stays visible.

## Known issues

- **The description is associated after mount.** Server-rendered markup lists a Prose or a HelpText in `aria-describedby` only after hydration. `useField` with `hasDescription` or `descriptions` doesn't have this gap.
- **Error under the control on phones.** The on-screen keyboard can cover the message under a focused field. The mitigation is in the docs (focus on submit, `scroll-padding`), not in the components, and the AT and usability run checks it. The error is linked from the first render whenever the field is invalid, in server-rendered markup too, and when an app moves focus to the field in an effect after submit. Tests: `field.test.tsx › focus on submit`.
- **WebKit is not automated.** Keyboard rows run in Vitest browser mode on Chromium. WebKit is not covered by the automated tests, so check Safari with your own users and assistive technology.
