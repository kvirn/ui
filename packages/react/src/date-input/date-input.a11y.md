# Accessibility contract: DateInput (DateInput.Root, DateInput.Day, DateInput.Month, DateInput.Year)

- **APG pattern:** none. There is no APG pattern for a date field made of text boxes. A date is a group of three labelled text inputs inside a `<fieldset>` with a `<legend>`, which is the pattern the GOV.UK Design System and other public-sector design systems use. Each box is a native input with its own label, so the browser can autofill it and dictation and screen readers can address it; how each assistive technology does so is recorded in the AT test record as it is tested. The one-field alternative, a `TextInput` with `masks.date()`, is preferred for most dates; the boxes stay supported.
- **Deviations:** none from APG. One deviation from the keyboard practice, approved by the maintainer (2026-10-04): **focus moves to the next box when the user's typing fills a box** (auto-advance), on by default, `autoAdvance={false}` turns it off. The practice says typing never moves focus (3.2.2 On Input (A)), so six guards and a visible hint make it predictable, and DateInput is the only exception (OneTimeCode, TextInput and every other control keep "typing never moves focus"). Decisions: three native text inputs, never `type="date"`; the order follows the region through `Intl` and a month-first result becomes day first; three Tab stops, no arrow-key stepping; the consumer writes the date example; `Fieldset.Root`'s `invalid` does not cascade, each box has its own `invalid`.
- **Native elements used:** `<fieldset>` and `<legend>` (the consumer's `Fieldset.Root` and `Fieldset.Legend`), `<div>` (`DateInput.Root`, and one per box), `<label for>` (the box label), `<input type="text">` with `inputmode="numeric"` (the boxes).
- **Status:** alpha candidate. Accessibility-reviewer pending. Manual AT is `pending`, including how screen readers announce the focus move.
- **Tests:** `date-input.test.tsx` next to this file. `date-input.stories.tsx` in `apps/storybook/src/components/date-input/`. The group's parts (`Fieldset.Legend`, `Fieldset.Prose`, `Fieldset.HelpText`, `Fieldset.ErrorMessage`): `fieldset.a11y.md`. The text keys of each box: `text-input.a11y.md`.

A DateInput is one question ("Date of birth") answered with three boxes: day, month and year. `DateInput.Root` renders the row of boxes and goes inside a `Fieldset.Root`, whose legend is the question and names the group. Each box is a `Field` with a visible label ("Day", "Month", "Year") and a native `TextInput`. It holds no form state: the value is the `value` prop and each change is reported up, or the native inputs keep it and a form submit reads it. It never parses or validates the date: that is the form's job.

Rules, tested in `date-input.test.tsx`:

- **Three boxes in a named group.** In a `Fieldset.Root` with a `Fieldset.Legend`, the group is named by the legend and each box by its own label (`date-input.test.tsx › the group is named by its legend and each box by its label`).
- **The group describes the whole date.** The auto-advance hint, the `Fieldset.HelpText` (the format example) and the `Fieldset.ErrorMessage` are in the fieldset's `aria-describedby`, in DOM order, not in the boxes' (`date-input.test.tsx › the hint and the error describe the group`).
- **Auto-advance (maintainer-approved 2026-10-04).** On by default; `autoAdvance={false}` is the opt-out. These six guards are what make it acceptable under 3.2.2 On Input (A), and each is tested:
  1. **Only the user's typing that fills a box, and never from the last box.** The input type is `insertText` and the box was shorter before the key; full is two digits for day and month, four for year, and digits only. The next box is the next one in the DOM, which is the Tab order (`date-input.test.tsx › typing the last digit of a box moves focus to the next box: year, month, day for sv-SE, and never from the last`, `… › it follows the order of the boxes: day, month, year, and month, day, year`, `… › your own order of children is the order it follows, not the locale’s`, `… › right to left: it still follows the DOM order`, `… › a disabled next box keeps focus where it is`).
  2. **Never on paste, drop, autofill, deletion, a prefilled or controlled value change, text that is not digits, or the edit of a box that was already full** (`date-input.test.tsx › paste, drop, autofill and deletion never advance`, `… › a value that changes from outside never moves focus`, `… › a box that is not full, and text that is not digits, never advance`, `… › an edit of a box that was already full never advances`).
  3. **Forward only.** Backspace and Delete edit the box and never move focus, not even in an empty box; Tab and Shift+Tab are native (`date-input.test.tsx › Backspace and Delete never move focus, not even in an empty box`).
  4. **Users are told before they type (3.2.2 On Input (A)).** A visible hint, `dateInput.autoAdvanceHint` (all five locales, overridable per provider and per instance), sits under the boxes and is in the group's `aria-describedby`. It exists only while `autoAdvance` is on, and it is not hidden (`date-input.test.tsx › the hint is visible text, in the group’s description, in sv and en`, `… › the instance’s messages replace the hint, and the hint needs no Fieldset hint`, `… › the hint is visible, and autoAdvance={false} takes it out of the description`).
  5. **`autoAdvance={false}`** is the opt-out, for teams that follow the stricter reading: typing never moves focus and the hint is gone (`date-input.test.tsx › autoAdvance={false}: typing never moves focus, and the hint is gone`). `useDateInput` has the same option and returns `autoAdvanceHint` (`date-input.test.tsx › the hook alone: getInputProps moves focus, and autoAdvanceHint is the message while it is on`).
  6. **The next box is selected,** so typing replaces a prefilled value (`date-input.test.tsx › moving focus selects the whole next box, so typing replaces a prefilled value`).
- **The field order follows the region** (`date-input.test.tsx › the order follows the locale: year first for sv-SE, day first for sv-FI, fi, nb and en`). `Intl.DateTimeFormat(locale).formatToParts` gives the order. A result that starts with the month (`en`, `en-US`) becomes day, month, year, because month first reads as day first for the EU readers this library serves. Writing `DateInput.Day`, `.Month` and `.Year` as children in your own order overrides it (`date-input.test.tsx › children override the locale’s order`).
- **`invalid` is per box.** The Fieldset's `invalid` marks the group's parts only (see Fieldset). A box with `invalid` (or named in `invalidParts`) gets `aria-invalid="true"` and `data-invalid` on its input, label and Field; the others stay valid. The group's one error is the message (`date-input.test.tsx › only the invalid boxes are marked invalid, and the group’s invalid marks none`).
- **`name` is a prefix.** `name="birth"` gives the boxes `birth-day`, `birth-month` and `birth-year`, which a plain form submit sends. A `name` on one box wins (`date-input.test.tsx › name is a prefix for the three inputs, and a box’s own name wins`).
- **Controlled by `value`.** `value={{ year, month, day }}` (all strings) sets the three boxes, and each change calls `onValueChange({ year, month, day }, { reason: 'input', part, event })` with the whole date as the boxes show it. Nothing is stored (`date-input.test.tsx › controlled: value sets the boxes and a change reports the whole date`).
- **Uncontrolled without `value`.** `defaultValue` (any of the three) sets the starting text; the browser keeps it, and `onValueChange` still reports the whole date (`date-input.test.tsx › uncontrolled: defaultValue and onValueChange`).
- **Never parsed, never fixed.** Leading zeros, letters and impossible dates stay as typed; the value is strings (`date-input.test.tsx › the value is the typed text: nothing is parsed or padded`).
- **`autoComplete="bday"`** on the Root gives the boxes the tokens `bday-day`, `bday-month` and `bday-year` (1.3.5 Identify Input Purpose (AA)) (`date-input.test.tsx › autoComplete bday sets the three tokens`).
- **Required and disabled** come from the Fieldset when the Root doesn't set them: `required` makes every box `aria-required` and `disabled` disables them natively (`date-input.test.tsx › required and disabled come from the Fieldset`).
- **Strings** are `dateInput.day`, `dateInput.month`, `dateInput.year` and `dateInput.autoAdvanceHint`, from the provider, the instance `messages` or the built-in English, in at least sv and en (`date-input.test.tsx › the labels follow the provider’s locale and the instance messages`).
- **No axe violations** in the default, invalid, disabled and read-only states (`date-input.test.tsx › has no axe violations in every state`).
- **Dev warnings:** a Root outside any group; a Day, Month or Year outside a Root (`date-input.test.tsx › warns when the Root is outside a group, and when a box is outside a Root`); a Root in a Fieldset that is neither `group` nor `required`, where an optional date would say so nowhere (`date-input.test.tsx › warns when the Fieldset is neither group nor required, and not when it is either`).
- **The optional marker is the legend's.** In a `group` Fieldset that isn't `required`, the legend ends with "(optional)", and no box does (`date-input.test.tsx › an optional date carries “(optional)” on its legend, never on a box`), also when the Fieldset is neither `group` nor `required` (`date-input.test.tsx › a Fieldset that is neither group nor required still keeps “(optional)” off the boxes`).

## Keyboard

- **Focus strategy:** native
- **Selection follows focus:** n/a
- **Arrows wrap:** n/a
- **Shortcuts:** none

All native, with one addition: DateInput handles no keys and never calls `preventDefault` on one, but **typing the digit that fills a box moves focus to the next box** (auto-advance, on by default, `autoAdvance={false}` turns it off). That deviates from the keyboard practice's "typing never moves focus" (3.2.2 On Input (A)), and the maintainer approved it for DateInput only, because a date is three short, fixed-length boxes and typing it without Tab is what people expect. The guards are in "Rules" above: forward only, never on paste, deletion, autofill or a changed `value`, never from the last box, a visible hint tells users before they type, and the next box's text is selected. The group is **three Tab stops**, one per box, in the field order, because each box is its own text input (the date is not a composite widget), and the arrow keys never step a value up or down (numbers are text). The legend, hint, labels and error are not Tab stops. Which box comes first depends on the locale (day first, or year first for sv-SE), and the table says "first" and "last" in that order. In right-to-left text the boxes flow right to left in DOM order, and Tab follows the DOM.

## Focus management

- Initial focus: not moved.
- Focus moves on its own in one case: the auto-advance (Keyboard above). It moves forward to the next box in the DOM, never back, never out of the date, and never to a disabled box.
- Trap: no.
- Restore to: not applicable.
- On error: DateInput never moves focus. The consumer moves it, to the first invalid box, or to the first box when the whole date is wrong.
- Never obscured by: nothing around the boxes clips the focus ring.

## Announcements

None. Nothing is live. In English, on entering the first box a screen reader reads the legend, "group", the group's description (the auto-advance hint "Focus moves to the next box when a box is full.", the consumer's example and, when invalid, "Error: …"); then the box's label, "edit text" and its state. Moving to the next box, by Tab or by the auto-advance, reads its label only: the focus move is announced as a new field. Whether that is clear enough while typing fast depends on the screen reader: test it with your users.

## Consumer responsibilities

- Leave `autoAdvance` on unless your service follows the stricter reading of 3.2.2 On Input (A). Never hide the hint: it is the advance notice (3.2.2). With the hook, render `autoAdvanceHint` as visible text and list its id in the group's `aria-describedby`.
- A `Fieldset.Root` around the DateInput, with a `Fieldset.Legend` that asks the question ("Date of birth"), first in the fieldset. The legend ends with "(optional)" in a `group` fieldset that isn't `required`.
- A native `<fieldset>` gets no dev warning and no marker for an optional date, so you write "(optional)" in the legend yourself, in your own language.
- **A `Fieldset.HelpText` with an example in the field order** ("For example 2007 3 27" when the order is year, month, day, "For example 27 3 2007" when it is day, month, year), under the boxes. KvirnUI supplies no example text: it names the fields, and the example is the service's (3.3.2 Labels or Instructions (A)). Write it in the order the boxes are in.
- One message for the whole date in `Fieldset.ErrorMessage`, after the boxes, and `invalid` on the wrong boxes only ("must include a year" marks Year, "must be a real date" marks all three). Say what is wrong and how to fix it (3.3.1 Error Identification (A), 3.3.3 Error Suggestion (AA)).
- Pass `value` and `onValueChange` from your form state, or `defaultValue` and `name` for a plain `<form>`. Validate the date yourself: DateInput never parses it.
- Carry forward a date the user already gave earlier in the same process, with `value` or `defaultValue`, so they don't enter it again (3.3.7 Redundant Entry (A)).
- A date of birth gets `autoComplete="bday"`. Don't set it on other dates (1.3.5 Identify Input Purpose (AA)).
- Pick the order from the page's locale, or deliberately override it when the service must match a paper form. Then the help text follows the order.
- For a date to pick near today, add a DatePicker button after the boxes: typing still works there. Don't use a DateInput for a date nobody knows by heart.

## Visual / modes

- Focus indicator: the TextInput's own, a ring at least 2 pixels thick with at least 3:1 contrast against its surroundings (2.4.13 Focus Appearance, AAA), on the focused box.
- Target size: each box is as high as a TextInput and wide enough for its digits, above the 24 by 24 pixel minimum of 2.5.8 Target Size (Minimum) (AA), also in the compact density. The year box is wider than day and month.
- Colour: an invalid box takes the TextInput's invalid state, a thicker edge in the error colour with no shift of the text, plus the group's message (never colour alone, 1.4.1 Use of Color (A)). A disabled box has a dashed edge; a read-only box has a solid edge.
- Forced colours (a user's high-contrast mode): the TextInput's system colours; every box keeps a visible edge and the message stays visible. That an invalid box's edge is thicker than a valid one's is reviewed by eye and in Windows Contrast Themes, not asserted by a test.
- Reduced motion: no motion of its own.
- Right to left: the boxes flow right to left in the order of the page, and digits stay left to right.

## WCAG SCs covered

- 1.3.1 Info and Relationships (A), 4.1.2 Name, Role, Value (A): a fieldset with a legend, a visible label for each box.
- 1.3.5 Identify Input Purpose (AA): `autocomplete="bday-day"`, `bday-month` and `bday-year`.
- 1.4.1 Use of Color (A), 1.4.11 Non-text Contrast (AA): the invalid edge's width and the message.
- 2.1.1 Keyboard (A), 2.4.3 Focus Order (A): three Tab stops in the field order, native keys. Auto-advance moves forward in that same order.
- 2.4.7 Focus Visible (AA), 2.4.11 Focus Not Obscured (Minimum) (AA). 2.4.13 Focus Appearance is AAA and is not counted toward the AA bar.
- 2.5.3 Label in Name (A), 2.5.8 Target Size (Minimum) (AA): a story checks the size of each box, also in the compact density.
- 3.2.2 On Input (A): auto-advance is not a change of context in the usual reading (the user stays in the same date, in the next of its boxes), and it is advised before the user types (the visible hint in the group's description), forward only, and off with `autoAdvance={false}`. The maintainer accepted this trade-off (2026-10-04). W3C's own explanation of 3.2.2 gives moving focus on to the next field of a phone number as an example that is acceptable when it is described to the user.
- 3.3.1 Error Identification (A), 3.3.2 Labels or Instructions (A), 3.3.3 Error Suggestion (AA): the legend asks, the help text gives the format in the field order, the error says what to do.
- 3.3.7 Redundant Entry (A): `value` or `defaultValue` carries a date the user already gave forward; carrying it forward is the consumer's.
- 3.3.8 Accessible Authentication (Minimum) (AA): if the date is part of an authentication step, paste is never cut and `autoComplete="bday"` autofill works, so it doesn't block a password manager or the browser.

## Known issues

- **`aria-describedby` on a `<fieldset>` isn't announced consistently by TalkBack.** See the Fieldset page.
- **An invalid box isn't linked to the group's error.** The box has `aria-invalid="true"`, and the error is in the fieldset's description, which screen readers read on entering the group. A box added to the error's description would repeat it three times. The AT run decides.
- **A year with fewer than four digits** (`0999`) always needs Tab: the box is never full.
- **A controlled parent that rejects a keystroke** still sees focus move when the box would have been full: the advance reads the typed text, not the value React keeps.
- **Pasting a whole date** ("27.3.2007") into one box isn't split across the three. It is out of scope.
