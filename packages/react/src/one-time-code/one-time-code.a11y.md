# Accessibility contract: OneTimeCode (Root, Input, Slot)

- **APG pattern:** none. A one-time code is one native text input. The name, description and state come from HTML and the Field (see the Field and TextInput contracts), and the masked typing rules from the mask engine. Prior art: GOV.UK "Confirm a phone number" (one input for the code) and `input-otp` (one input with drawn slots).
- **Deviations:** none from APG. Decisions: one native input with boxes that only draw it (the slots), `data-caret`, `data-selected` and `data-ready`, no auto-advance, no auto-submit, a `pattern` in place of a length with drawn separators, and the mask.
- **Native elements used:** `<input type="text">` (Input), `<div>` (Root, no role), `<span aria-hidden="true">` (Slot, and the separator).
- **Status:** alpha candidate. Accessibility-reviewer pending. Manual AT is `pending`.
- **Tests:** `one-time-code.test.tsx` next to this file. `one-time-code.stories.tsx` in `apps/storybook/src/components/one-time-code/`.

A OneTimeCode shows a code sent by text message or email as a row of boxes, one per character, shaped by a `pattern` (`999999`, `****-****`, `AA-9999`) with a dash drawn between the groups. Underneath it is one native input: autofill events, paste, undo and the screen reader work on that one field (tested); real SMS autofill, password managers and dictation are checked by hand in the manual AT run (`pending`). The boxes are a drawing of its value, caret and selection, hidden from assistive technology. Nothing moves focus and nothing submits on its own (3.2.2).

Rules, each with an automated test:

- **One field.** The row has exactly one textbox. Its accessible name is the Field's visible label (2.5.3 Label in Name, A), and its description is the Field's help text, then the error. The slots are never in the name, the description or the tree.
- **The attributes** in the table above, on every input. The mask is `masks.oneTimeCode({ pattern })`: `9` a digit, `*` a letter or digit, `a` a letter, `A` an upper-case letter, `&` an upper-case letter or digit (all ASCII), and `-` a separator that sits between two of them. A pasted `123 456`, `123-456` or "Your code is 123456" ends as `123456` for `999999`, and `abcd1234`, `abcd-1234` and `abcd 1234` all end as `abcd-1234` for `****-****`. There is no `maxlength` and no rewrite during an IME composition. An invalid pattern (an unknown character, a `-` first, last or doubled, no character symbol) throws a `RangeError` that names the character and its position.
- **Upper-case symbols upper-case what is typed.** In `A` and `&` a typed `a` is placed as `A`: the boxes show exactly what the input holds. `a` and `*` keep the case as typed.
- **The value includes the separator** (`abcd-1234`), as the boxes and the message show it. `onValueChange` details carry `unmaskedValue` (`abcd1234`) and `onComplete(value, unmaskedValue)` gets both.
- **One cell per pattern position.** `slots`, `getSlotProps(index)` and `OneTimeCode.Slot index` share one index: position _i_ of the pattern draws position _i_ of the value. A separator cell is `aria-hidden` and has no state. `isComplete` ignores the separators.
- **State from the input.** The slots draw what the input holds: its value, read again whenever the `value` prop or the hook's own state changes (so autofill, a controlled `value`, and a form reset are drawn as they are), and its caret and selection from `onSelect`. `data-active` is on the one character slot where the next character goes while the input has focus and nothing is selected: the first character slot at or after the caret, never a separator. `data-caret="before"` says the caret is before that slot's character. `"after"` is on the last character slot of a complete code with the caret after it, and on the character slot before a `-` that is in the value when the caret sits just before that dash (the user stepped back over it), so the two sides of a separator don't look the same. `data-selected` is on the filled slots a selection covers. None of them is set while the input has no focus.
- **Pattern facts on the Root.** `data-character-count` (the character symbols in the pattern: `8` for `****-****`) and `data-separator-count` (the `-`: `1`, or `0` for none) are always rendered, on the server too. The theme reads them to size the row and to decide when to fall back. They are styling facts, not exposed to assistive technology, and the headless package sets no style from them.
- **Ready flag.** `data-ready` is set once the hook has started. It first runs the input's current value through the mask (writing it back only if it changed), so what the browser or a password manager filled in before the script ran is drawn as the mask would have shaped it, and an uncontrolled value never hides a character past the pattern. A controlled `value` is the consumer's and is drawn as it is, so one that is too long or has a separator hides characters from sighted users while a screen reader reads all of it: keep it to what the mask would produce. The mount step is silent: it calls neither `onValueChange` nor `onComplete`, so a code autofilled before the script ran doesn't report completion (the submit button still covers it). The default theme draws the slots only then.
- **A press on a slot** (a box, or a gap) focuses the input natively. A single click on an empty slot puts the caret at the end of the code, and on a filled slot before its character. A separator is not a target: a press on it or in the gap goes to the nearest character slot. A double click, a drag and a long press keep the browser's selection.
- **No auto-advance, no auto-submit.** Typing the last character moves no focus and submits nothing. `onComplete(value)` is a callback for consumers who check early.
- **Field state.** `data-invalid` and `data-disabled` come from the nearest Field (or the Root's `disabled`), on the Root and on every slot.
- **Dev warnings:** an Input or Slot outside a Root, a Slot whose index is not a position of the pattern (separators count), an Input with no accessible name, and an Input in a Field with no description (a `Field.Prose` above or a `Field.HelpText` under: the length and the groups must be said, 3.3.2 Labels or Instructions, A).

## Focus management

- Initial focus: not moved. The component never focuses anything, including when the code is complete or when a wrong-code error shows (the page focuses the error summary or the field, as for any field).
- Trap: no.
- Restore to: not applicable. The input is always rendered, and never disabled while a code is checked: a disabled input loses focus, which lands on `body`. Use `readOnly` and say "Checking the code" through the Announcer (see Consumer responsibilities).
- Never obscured by: the focus ring is the input's own ring, drawn outside the whole row, and nothing in the row has overflow, so it is not clipped (2.4.11 Focus Not Obscured (Minimum), AA; 2.4.13 Focus Appearance, AAA). Consumers with a sticky header set `scroll-padding`.

## Announcements

| Event                                                    | Message key (i18n)                                                                                                 | Politeness |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------- |
| A character the mask refuses (a letter in a digits code) | `mask.characterNotAllowed` ("Only digits can be entered here.", or "Only letters and digits can be entered here.") | polite     |
| A character refused because the code is complete         | `mask.maximumLength` ("You’ve entered all 6 characters.")                                                          | polite     |

Both are the mask's, throttled to one message per field every three seconds, and need the `KvirnProvider`. `announceRejections={false}` turns them off for a consumer who shows their own. The component adds no strings of its own. Completing the code announces nothing: the user hears their own typing.

## Consumer responsibilities

- **A visible label that says where the code is,** in the user's words ("Kod från sms:et", Code from the text message; "Code from your authenticator app"), not "OTP" or "verification code". The label is the accessible name (2.5.3 Label in Name, A).
- **A description above the boxes, a `Field.Prose` in the Field, with the length, the groups and where to find the code** ("Koden har 8 tecken i två grupper om 4. Du hittar den i sms:et som vi just skickade", The code has 8 characters in two groups of 4. You find it in the text message we just sent). The slots are hidden from screen readers and disappear in the fallback, so the description is the only place they learn the length and the groups (3.3.2 Labels or Instructions, A). A dev warning fires without one.
- **Errors in text,** under the row, linked by the Field: "Enter all 6 digits of the code", "The code doesn't match the one we sent. Check the text message and enter the code again." Never blame, and keep the code in the field after a wrong-code error so the user can fix one digit (3.3.1 Error Identification, A; 3.3.3 Error Suggestion, AA).
- **Keep a submit button.** Never submit from `onComplete` without telling the user in advance that the code is checked as soon as it's entered (3.2.2 On Input, A), and never clear the field on a wrong code.
- **After a wrong code,** when focus is still in the field, announce the visible error text once, politely, through `useAnnouncer`, and set the Field invalid. If focus was on the submit button, move focus to the field (its description reads the error) and don't announce as well.
- **While the code is being checked, use `readOnly`, not `disabled`,** so focus stays, and say "Checking the code" through the Announcer.
- **Never `type="password"`, never block paste, and keep `autocomplete="one-time-code"`.** The user must see what they enter, and a password manager or SMS suggestion must be able to fill it (3.3.8 Accessible Authentication (Minimum), AA).
- **Write the `pattern` the way the message groups the code** (`****-****` for "ABCD-1234", `999999` for "481920"). A pattern that groups a code the message shows ungrouped, or the other way round, makes the user doubt what they see. Letters-and-digits codes should avoid look-alikes (`0`/`O`, `1`/`I`/`l`).
- **A service that wants the code without the dash** reads `unmaskedValue` (`onValueChange` details, `onComplete`'s second argument), or strips the `-` from the submitted value.
- **Countdowns, "Send a new code" and timeouts** are yours to build. The code's validity may be essential (2.2.1 Timing Adjustable, A), so say how long it is valid in the description, offer "Send a new code" as one action that keeps the page and its input, and never end the session or clear the form when a code expires.
- Everything in the TextInput and Field contracts still applies.

## Visual / modes

- Focus indicator: on keyboard focus, the input's own ring around the whole row, with at least 3:1 contrast against the background (2.4.7 Focus Visible, AA; 2.4.13 Focus Appearance, AAA). It is set by `data-focus-visible`, or by `:focus-visible` before the script runs. A click shows no ring (an invalid field shows the ring on any focus, and keeps its error-coloured edge): the active box's edge shows the focus, and the plain field's edge turns heavier in the focus colour. The box where the next character goes also has a heavy focus-coloured edge and a static caret, and selected boxes a tinted fill with the same edge, never colour alone.
- Target size: the input covers the whole row, so it clears 2.5.8 Target Size (Minimum, AA) in both densities, and in the default comfortable density it also clears 2.5.5 Target Size (Enhanced, AAA).
- Colour: the box edges have at least 3:1 contrast against the background (1.4.11 Non-text Contrast, AA). An invalid field has a heavier error-coloured edge on every box, never colour alone: the message under the row carries it. A disabled field has a dashed edge, and its characters are muted. Complete has no look of its own: a tick or green edge would read as "verified". The theme's contrast check covers every colour pair.
- Forced colours (the system's own colour scheme): the theme shows the plain input as a normal text field in the system's colours, with a heavier edge in the system text colour when invalid and a dashed grey edge when disabled. The focus edge and the keyboard ring use the system highlight colour, and a click's transparent outline is painted by the system. The slots are hidden. This is reviewed in a story, not yet in an automated display-mode check.
- Reduced motion: the boxes' edge and fill change gradually only when the person has not asked for reduced motion. The caret never blinks, in any setting (2.2.2 Pause, Stop, Hide, A).
- Reflow (1.4.10 Reflow, AA): the boxes shrink, then the plain field shows instead of wrapping, so there is no horizontal scrolling at 320px width, in a card, at 200% text or at 400% zoom. Switching is CSS only: the same input keeps its value, caret and focus. This is reviewed in the stories, not yet checked by an automated test.
- Text spacing (1.4.12 Text Spacing, AA): the boxes don't depend on the input's text metrics, have no fixed height and are centred with flex, so characters are not clipped.
- Before the script runs (`data-ready` not yet set) the plain input shows, so what is typed or autofilled meanwhile is visible as the browser draws it, with no mask and no `maxlength`. When the script starts, that value goes through the mask once (separators and characters that don't fit are dropped, and it is written back only if it changed), so the boxes draw exactly what the field holds and the form never submits characters the boxes hide. A controlled `value` is the consumer's and is drawn as it is. A form reset does the same for the default value.
- Right-to-left (RTL) pages: the code is an identifier, so the input has `dir="ltr"` and the row of boxes reads left to right, at the start (the right) of the column. ArrowRight still moves to the next character.

## Known issues

- **Screen readers read the dash** in a grouped value ("A B C D dash 1 2 3 4"). Accepted: the separator is part of the value the boxes show, and the help text explains the groups.
- **Screen readers read a digits value as a number** ("four hundred eighty-one thousand…") until the user moves through it by character. The same as any numeric field.
- **Password-manager icons** can cover the last box. Not detectable in CSS; waits for the manual matrix.
- **The browser's autofill tint** shows in the narrow gaps between the boxes, under the opaque boxes. Accepted: it tells sighted users the code was filled in.
- **Undo** after the mask inserted a literal can't be kept without `execCommand`. A grouped pattern (`****-****`) has a literal, the dash, so undo after the mask put it in can step back over it in two presses. A pattern without a separator has no literals, and undo is native.
- **WebKit is not automated.** The keyboard rows are tested automatically in Chromium only, not in WebKit (Safari's engine), and the manual assistive technology (AT) matrix is `pending`.
