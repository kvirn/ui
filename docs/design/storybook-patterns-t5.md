# Design spec: Storybook Patterns and Content types, T5 slices

- **Status:** Draft; Q11–Q17 decided by the maintainer 2026-10-13 · **Designer:** ux-designer agent · **Date:** 2026-10-13
- **Plan:** Plan 0095 T5. Split from [storybook-patterns.md](storybook-patterns.md) (Q17), which holds the brief, IA, frame, site chrome, fixture world, visual spec and shell annotations; this file adds the remaining patterns and content types. Feeds [municipality-reference-site.md](municipality-reference-site.md) slices R4–R10 (Plan 0053).

## 1. Approach

Ordered so the reference site's slices (Plan 0053 R4–R10) are unblocked first (Places and contacts, statement and forms, sign-in, news and events, search), then by survey coverage and by what each slice needs from an earlier one. One slice is one engineer brief. **Recipe** = a story of literal JSX from shipped parts, no package code (D11); every T5 pattern is a recipe, since none adds behaviour a shipped part or the app doesn't own. The content types hold the recipes' JSX (S4). No new token, colour pair, i18n key or library component in any slice; pattern CSS, if a layout needs it, goes in `patterns.css` (D6). Each story: every state, 320px and wide, RTL, forced colours, axe in four themes; title `Patterns/<Group>/<Name>`; its Docs page lists the parts. Text is English (D10). Fixture clock: Monday 12 October 2026 ([storybook-patterns.md](storybook-patterns.md) §8). D-numbers are Plan 0095 decisions.

## 2. Shell rules (each pattern below names the ones it applies)

| #   | Rule                                                                                                                                                |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | Headings: the recipe fixes no level; `Heading as` follows the page (one `h1`, no skipped level, stop at `h3` on resident pages)                     |
| R2  | No landmark of its own. A `nav`, `form`, `search` or region only when named and distinct on the page; a list of links in content is not a `nav`     |
| R3  | Lists are `List` or `Grid.Root as="ul"`, so the count is announced                                                                                  |
| R4  | Link text makes sense alone (2.4.4); an item has one link, in its heading; no clickable card                                                        |
| R5  | DOM order = visual = focus order at every width; nothing sticky (1.3.2, 2.4.11)                                                                     |
| R6  | 320px, 400 %, 1.4.12: wraps, never truncates; a wide table scrolls in `Table.ScrollRegion`, a Tab stop only while it overflows                      |
| R7  | Dates are `<time dateTime>` written with `useFormat`, never only relative ("2 days ago")                                                            |
| R8  | No third-party request (rule 7): no map, embed, feed, share widget or newsletter iframe; a plain link out is fine                                   |
| R9  | Status in words (plus icon where the part has one), never colour alone (1.4.1); a closed or unavailable action is text, never a dimmed link         |
| R10 | Focus never on `body`; nothing announced on load; a client-side result change is announced once, politely, through the provider's Announcer (4.1.3) |
| R11 | Content in another language carries `lang` (3.1.2)                                                                                                  |

## 3. Slices

### S4 Content types become components (decision 2026-10-13; first)

- **Move** Start page, Subpage, Content page and Documentation page to `packages/patterns/src/content-types/<name>/<name>.tsx`, and the shells (`kvirnby-chrome.tsx`, `shell.tsx`: Kvirnby and KvirnUI docs) to `content-types/shell/`. Export from the sub-entry `@kvirn-ui/patterns/content-types` (Q11).
- **Shape.** One component per page type, literal English JSX, rendering the slot only (D12: breadcrumb, sidebar, `main#main`; never header, alert or footer). Props are state only, one per story state that changes content (`eService: 'open' | 'closed'`, `children: 3 | 7` on Subpage); no content props, no data objects. A client module (`'use client'`), so a docs server page can import it (Plan 0100 risk: compound parts are `undefined` across the boundary).
- **Stories** render the component inside `withShell`, keep `expectPageOutline` and the shell story; story ids unchanged. The source panel shows the module text (`?raw` into `docs.source.code`), so the JSX stays copyable.

### S5 Full-page example route (Plan 0100 G6, moved here)

- **Needs R0** (Plan 0053, [municipality-reference-site.md](municipality-reference-site.md)): R0 moves the docs routes into `app/(docs)/` with their own root layout, once; S5 adds a sibling route group on that.
- The example route group has its own root layout: `<html lang="en">`, `theme.css` and `@kvirn-ui/*` only, no `docs.css`, **no docs shell**, so the page has one `banner`, `main` and `contentinfo`. `robots: noindex`; `<title>` "{Page type} example – Kvirnby (fictional municipality) – KvirnUI".
- One route per content type, rendering shell + content type in the default state. `SiteHeader.Notice` first in the banner: "Kvirnby is a fictional municipality. This page is a KvirnUI example." with a link back to the type's docs page (reference §6). The content-type gallery page links to it ("Open the full page").
- Each content type added in a later slice gets its route in that slice.

## 4. Decisions (maintainer, 2026-10-13)
