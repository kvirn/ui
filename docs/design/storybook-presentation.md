# Design spec: Storybook presentation for KvirnProvider, Button and Link

- **Status:** Draft
- **Designer:** ux-designer agent · **Date:** 2026-10-01
- **Plan:** Plan 0005 (to be written) · component stories themselves: [Plan 0002](../plans/0002-kvirn-provider.md), [Plan 0003](../plans/0003-button-and-link.md)
- **Type:** docs page (workbench presentation)
- **Depends on:** [default-theme-button-link.md](default-theme-button-link.md) for tokens, recipes and states

> **Update 2026-10-01 (Plan 0008):** stories are args-first on the real component, with a Docs page each (`@storybook/addon-docs`) and an `introduction.mdx`. There is no story wrapper or page heading any more: `lang`, `dir` and the theme are set on `<html>`, and the body is the canvas (`.storybook/preview.css`). The Theme toolbar became **Mode** (light, dark, system) and **Contrast** (standard, more). The fixed-theme story exports are gone: four `storybook*` Vitest projects run every story once per theme instead. Where this spec says otherwise, the story-convention decision wins.

> **Update 2026-10-01 (the theme-delivery decision revised, the theme-prototype decision):** the separate headless and `Default theme/*` sections became one set of stories per component (`Components/Button`, `Components/Link`, `Foundation/KvirnProvider`), all styled by `theme.css`. The Theme toolbar has a "None (unstyled)" option instead. The example fixture moved to the docs site.

## 1. Brief

- **Users:**
  - Maintainers and contributors, including agents, who use Storybook as a workbench and review surface. That covers the axe-as-test results, the design review screenshots and the e2e runs, which target Storybook.
  - Secondary: evaluating developers, if Storybook is published next to the docs site (Open question 1).
- **Hardest-case user:** a maintainer who uses a screen reader or keyboard only and reviews a Button change in dark high contrast, in Finnish and in RTL. They need to find the right story, set those modes without a mouse, and trust that axe checked what they are looking at.
- **Job to be done:** When I change or review a component, I want to see every state of the headless component and of its default-theme styling, in every theme, locale and direction, so I can catch regressions before they ship.
- **Context:** desktop, daily or weekly use, with Storybook's own UI. Reviews take a few minutes per story.
- **Constraints:**
  - Headless stories must stay unstyled, so they prove the packages ship zero CSS.
  - No new dependency without the maintainer's approval, and that includes Storybook addons such as `addon-themes` or `addon-docs`.
  - No telemetry.
  - axe runs on every story (gate 2), and the a11y test setting stays at `'error'`.
- **Success criteria:**
  - Every default-theme story passes axe in each of the four themes.
  - A reviewer can reach any theme, locale or direction combination in 3 toolbar changes or fewer.
  - Story names say which state they show, in plain words.
  - The provider's theme-store stories keep passing, unaffected by the new theme toolbar.
- **Evidence:** none. The current preview has Locale, Direction and Forced colors toolbars, and axe-as-test.
- **Assumptions and research questions:**
  - Assumption: maintainers want the headless and styled stories separated rather than mixed. → Research question: in the first review sessions, do reviewers look for both views side by side?

## 3. Flow

Maintainer review flow:

1. Open Storybook. The sidebar shows **Introduction**, **Foundation**, **Primitives** and **Default theme**, in that order.
2. Read _Introduction / About this Storybook_ on first use. It explains the toolbars, the difference between headless and default-theme stories, and what axe does and doesn't cover.
3. Open _Primitives / Button / Focusable when disabled_ and check the behaviour, unstyled.
4. Open _Default theme / Button / States_ and check the look.
5. Change the toolbar: Theme → "Dark, high contrast", Locale → `fi`, Direction → `rtl`. The story re-renders, and the a11y panel shows the axe result for the current view.
6. For proof in CI, check the fixed theme stories (_Default theme / Button / Dark, high contrast_). Their axe results are the gate. The toolbar results are for exploration only.

Unhappy paths:

- **A story fails axe:** the test fails in `vp test run`, and the a11y panel shows the violation. The Introduction explains that the fix belongs in the recipe or the component, never in a disabled rule.
- **The theme toolbar and a story disagree:** a fixed theme story sets `globals.theme`, which overrides the toolbar for that story. Storybook shows the toolbar value as locked for that story.
- **Theme toolbar used on a headless or provider story:** it has no visible effect on headless stories (they are unstyled; only `color-scheme` changes native controls). Provider stories opt out (see §6). The Introduction says this.
- **A Sámi string is missing:** that fixture text renders in English with `lang="en"` on its own element, and the story shows the note `stories.fixture.samiPending`.
- **Forced colours toolbar set to "active":** this only marks the story. Real emulation runs in the `chromium-forced-colors` e2e project. The toolbar description says so already, and the Introduction repeats it.

## 5. Structure

The Storybook manager UI isn't ours to lay out. These rules cover the story canvas.

```
Default-theme story canvas (decorator), all widths
[div.kv-story-canvas  lang dir]      canvas bg · text colour · font-family-sans · padding space-6 (space-4 below 40rem)
  [main]                              one <main> per story, so axe's landmark rules and the e2e reflow checks see real page structure
    h1 (visually present)             story subject, e.g. "Knappar" / "Painikkeet" from fixture text, so the heading outline is real
    …story content…
```

- Headless stories keep the existing decorator (`div lang dir`) and get **no** canvas styling.
- The heading outline per story is `h1` (subject), then `h2` for each group in matrix stories ("Primär", "Sekundär", "Farlig" … per locale).
- Matrix stories (`States` and the four theme stories) don't use a table. Each variant gets an `h2` ("Primär", "Sekundär", "Farlig" per locale), then each state gets a `p` naming it ("Inaktiverad") directly **before** its button. The state name stays out of the button label, so the accessible name under test is the real label. This reads well linearly and reflows at 320px.

### Default theme/Colours (optional, P2)

One story per theme. It shows a list, not a table, of token name, swatch, hex value, and the measured ratio against `canvas` for text tokens. Swatches have a 1px `border-control` edge so light swatches stay visible. The text is the token name and value, never colour alone. This gives design reviewers a quick check of `tokens.ts` against DESIGN.md.

### States

The Button and Link state tables are in [default-theme-button-link.md §6](default-theme-button-link.md#6-visual-specification). This spec adds no states. **Hover and active** can't be rendered statically without a new addon, so:

- axe doesn't check them. Their contrast is covered by `theme:check`, which measures `on-primary` on `primary-hover` and `danger-hover`, `text` on `primary-subtle`, and `primary-hover` on `canvas` and `surface`.
- Design review takes Playwright screenshots with `page.hover()` into `/tmp` (the design skill procedure).

### Modes

- **Four themes:** the toolbar is for exploration. The fixed theme stories are the gate.
- **Forced colours:** the toolbar marks only. Emulation runs in e2e.
- **RTL:** the toolbar, plus a fixed `Right to left` story per component.
- **Reduced motion:** the `chromium-reduced-motion` e2e project runs the default-theme stories. Assert that a computed `transition-duration` is `0s` on `.kv-button`.
- **320px:** the `reflow-320` e2e project runs every default-theme story. There must be no horizontal scroll on the document.

### New or changed tokens

None. The canvas uses existing tokens only.

## 7. Accessibility annotations

- Every default-theme story renders one `main` and one `h1`, so axe landmark and heading rules are meaningful and the e2e reflow checks see page-like structure.
- Every story's content has a correct `lang`. The canvas gets `localeProps`, and untranslated Sámi strings carry `lang="en"` (3.1.2).
- Fixture explanations (state names, the danger note, the disabled reason) are real text, never `title` attributes or tooltips.
- The Storybook manager UI is third-party. Its own accessibility is outside our contract, and the Introduction says so plainly without judging it.
