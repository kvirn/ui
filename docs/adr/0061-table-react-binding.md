# ADR-0061: Table's React binding: one instance per `useTable`, options handed over silently, and the names of the parts

- **Status:** Proposed
- **Date:** 2026-10-04
- **Deciders:** Plan 0026 (the Table part of ADR-0035 and ADR-0059). The details below are proposed and open to change in review.
- **Tags:** architecture, api, a11y

## Context

ADR-0059 decides that `useTable(options)` creates the TanStack Table instance through `createTable`, and ADR-0035 decides the parts and what they say. Building them needed decisions that those leave open: how a React render and a TanStack Table instance agree on options and state, how a part that doesn't know its table gets typed, how a checkbox is named by a row it is not inside of, and a few things where the plan's text and valid HTML disagree.

## Decision

1. **`createTable` returns `{ table, store, updateOptions }`.** `store` is `table.store` as a `ReadableStore`, built structurally (only `get` and `subscribe`), so `@tanstack/store` stays imported in `core/src/store/` alone (ADR-0003). `useStoreSelector` reads it.
2. **Options are handed to the instance while rendering, and that notifies nobody.** `useTable` calls `updateOptions(options)` on every render, before anything reads rows, so `data`, `columns` and controlled `state` are current in the render that has them. TanStack publishes state when options change, and a notification during a render would make React warn that a component is updated while another renders. `updateOptions` suppresses notifications while it runs: the render in progress already reads the new state through `useSyncExternalStore`, and a change made afterwards (a sort) notifies as usual. The alternative, `renderPhaseReactivity` from TanStack, needs atom primitives from `@tanstack/store`, which only `core/src/store/` may import.
3. **Sorting never goes multi.** `toggleSorting(undefined, false)` is called, so a column's own `enableMultiSort` or a Shift+click can't reach it either. The next direction (`getNextSortingOrder`) is read before the toggle, so the announcement is right when state is controlled and doesn't change on the same tick.
4. **TanStack's feature-gated APIs are reached with type guards, not casts.** A column, row or table has the sorting, selection or expanding API only when its feature is registered, at run time and in its type. The parts work with any features, so `hasColumnSorting`, `hasRowSelection`, `hasRowExpanding` and `hasTableRowSelection` check for the API and narrow the type.
5. **A part gets its types from what it is given, through an untyped context.** `Table.Root` provides the `useTable()` result as an `object`, and `useTableContext<TFeatures, TData>()` gives its type back with a type guard that checks its shape. A part infers `TFeatures` and `TData` from the `row`, `cell` or `header` it receives, which come from that same table. `Table.Body`'s function gets the row typed with the constraint (`Row<TableFeatures, RowData>`); read values with `cell.getValue()` or write the generics (`<Table.Body<typeof features, Case>>`).
6. **A row's checkbox is named by itself and the row header cell.** One element per part rules out a hidden text element next to the checkbox, so the checkbox has `aria-label` ("Select") and `aria-labelledby` pointing at its own id and the row header cell's id. This is the accessible name computation of the ARIA specification (step 2C inside a `aria-labelledby` traversal) and is how the ARIA Authoring Practices name "Delete" buttons. The expand button is named by its own visible text instead (item 16). The ids are made from `useId` and the row id with every character that isn't a letter, digit or hyphen escaped, because a space in an id breaks `aria-labelledby`.
7. **`Table.Empty` is a `<tbody>` with one row and one cell.** The plan puts `<Table.Empty />` next to `Table.Body`, inside the table, where a `<tr>` is invalid HTML (React warns about it). A `<tbody>` is valid there and can come after the body, so the example stays valid. The `<td>` has no class of its own, and the row is not a `<tr class>`: the theme styles `.kv-table-empty > tr > td`.
8. **Spacer, detail and empty rows span what is drawn.** The columns of the model undercount when a table adds cells that aren't columns (a checkbox cell), so the hook reads the header row's cells' `colSpan` from the DOM after each render, and falls back to the leaf column count before that.
9. **A header row gets `aria-rowindex` from its header group.** `Table.Row` takes an optional `headerGroup` for this, so a virtualized table's header rows are numbered with the body rows, as `aria-rowcount` counts them.
10. **The scroll region is named by the caption and a Tab stop only while it scrolls.** Its own `aria-labelledby` and `tabIndex` win over the hook's, so a table named by a heading can name its region the same way. It is measured with a `ResizeObserver` through `Env` (ADR-0003).
11. **Select-all selects every row of the table.** `toggleAllRowsSelected` is used, not the page variant. The count it announces and the name `selectAllRows` can be overridden per instance for a paginated table. A page variant can be added when the Pagination component exists.
12. **No range selection.** TanStack's Shift+click range selection is not used: `row.toggleSelected` is called directly, which doesn't move the range anchor. Like multi-sort, range selection is a key combination the Table pattern doesn't define, and it would have to be documented and tested.
13. **The sort icon is drawn by the Table, not taken from the icon set.** The design spec (D1) asks for a built-in `sort` icon, which changes the icon API and needs its own ADR. Until then `Table.SortButton` draws an `svg.kv-table-sort-icon`: two small chevrons while the column is sortable, the built-in up chevron's shape for ascending and the down chevron's for descending. The three states differ in shape, so colour is never the only difference. Follow-up: add `sort` to the icon set (amend ADR-0024 or `icon.md`) and use `<Icon>` here, so an app's icon registry can replace it.
14. **`Table.Empty` shows "Loading rows." while the table loads and has no rows** (design spec D3), and ignores its children then, so it never says there is nothing while rows are on their way. The empty text and `loadingText` are in the hook's result.
15. **The scroll region sets `--kv-table-head-block-size`** inline, from a `ResizeObserver` on the head, for every table (not only a virtualized one), because a bounded region with a sticky head needs the scroll padding too (2.4.11). The theme turns it into `scroll-padding-block-start`. It is geometry, like `--kv-popup-width`. A virtualized table also sets an inline `inline-size` on each column header from TanStack's column size (`columnSizingFeature`, re-exported), which a fixed layout reads from the head. `data-overflowing` is set with `tabIndex={0}`.
16. **The expand button is named by its visible text and the row header** (design spec R1): its default content is "Details" and a chevron, and `aria-labelledby` points at itself and the row header cell. The expand column's header holds the same text visually hidden (R2, `kv-table-visually-hidden`, `expandButtonText` in the hook's result). Both checkbox parts render `kv-checkbox` as well as `kv-table-select-checkbox`.
17. **Numeric columns are classes the consumer adds** (`kv-table-column-header--numeric`, `kv-table-cell--numeric`, `kv-table-row-header--numeric`), not a reading of `columnDef.meta` (design spec D4). A shorthand is a later API decision.
18. **A row checkbox is 24px, with no extended hit area.** The design spec (§6.6) grows the target to 44px (32px in compact) with a `::after` on the input, but a click just outside the box did not toggle it in Chromium (e2e): an input doesn't take hits on what its pseudo-elements draw outside its box. The 24px box meets 2.5.8 (AA). A larger target would need a label or a wrapper element, which one-element parts rule out; a later ADR can add one.

## Consequences

- Positive: a render and a TanStack Table instance agree without React warnings, the accessibility rules of ADR-0035 hold for any set of features, and a static table needs none of it.
- Negative / trade-offs:
  - `Table.Body`'s children function is typed with the constraint unless the generics are written.
  - The checkbox names depend on `aria-label` inside an `aria-labelledby` list; the manual AT run checks them in every combination (pending).
  - A header row's `aria-rowindex` needs `headerGroup` on the Row, and the column count is read from the DOM, which is one render late during server rendering.
  - There is no range selection and no "this page" select-all yet.
